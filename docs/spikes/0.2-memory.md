# Spike 0.2 (memory half): large-document memory, and the renderer fix

Owner: the render role (Wave 2). Reference Mac: Apple M4, 16 GB, macOS 27, Rust 1.98.1 `--release`,
2026-10-06. Linux and Windows are **not measured** (the harness has a `/proc` reader for Linux, untested
here; Windows has none). Everything below reproduces with the commands at the end.

## Verdict (ARCHITECTURE section 1.2 script against the real renderer role)

The script is: open -> scripted full scroll (per page one 500 px preview and four 512 px tiles at bucket 2)
-> whole-document search -> 50 section re-opens (L1 merge at k > 16, tile after each) -> idle 10 s. The
renderer is the real role in a **sandboxed child process**, fed by file handle and shared-memory
sections; the harness plays host and engine (qpdf opens the file in the harness process). Both are
sampled at 10 Hz; per-process peaks also come from the kernel (`ri_lifetime_max_phys_footprint`).
Footprint is macOS `phys_footprint`, MB.

| File | renderer peak | renderer settled (budget 120) | engine peak | engine settled (120) | whole-app peak* (400) | whole-app settled* (250) |
|---|---:|---:|---:|---:|---:|---:|
| large-2000p-text | 11.0 | **4.0** | 8.7 | 8.7 | 160.9 | 98.1 |
| large-1000p-images | 65.4 | **4.9** | 6.2 | 6.2 | 206.0 | 96.5 |
| large-objects | 137.7 | **3.2** | 100.5 | 100.5 | 297.1 | 185.3 |

| large-single-page | 220.2 | **3.6** | 2.2 | 2.2 | 277.2 | 87.4 |

\* The shell/webview and the host's tile caches are not running in the harness (no GUI may be launched
here). They are added as documented constants and shown separately in the raw output: **shell 77.4 MB**
(Spike 0.1, macOS idle median of 5 runs, includes the webview), and **host tile caches** estimated from
the bytes actually delivered (L1 soft cap 48 MB plus previews at a third of raw, cap 16 MB; 64 MB after a
full scroll of a big file, about 4 MB for a one-page file), trimmed to 8 MB when settled. `peak_bound`
(sum of per-process lifetime peaks) is within 3 to 20 MB of the sampled peak in every row. The CI
producers must replace the constants with a real run of the app.

All four large files pass the renderer's 120 MB settled budget with a wide margin, and the whole-app
estimate passes both gates on every file. Before this work the renderer was at 648 MB (images), 261 MB
(single page) and 140 MB (large-objects) settled, and 104 MB (text, passing).

What still fails or is thin, stated plainly:

* **large-objects-objstm engine peak is 131.5 MB** (115 MB settled by the median of the last 2 s). The
  engine's qpdf object table, not the renderer, is now the largest single cost on the two large-objects
  files; the lazy per-operation engine proposed below still applies.
* **The renderer only meets the budget on macOS when the allocator environment is set** for files whose
  parse state is large (see root cause 1). Without it: large-objects settles at **140.8 MB (fails)** and
  whole-app settled 322.8; large-single-page 87.3 (passes); images 86.9 (passes); text 30.8 (passes).
  The governor alone is enough for three of the four files; the environment makes it 3 to 5 MB for all.
* Re-opening a 1.6 M-object file costs **200 to 400 ms** (xref re-parse), so edit -> tile p95 is
  361 ms (classic xref) and 199 ms (object streams) on those two files. The 100 ms target is for ordinary
  files (below). This is PDFium's xref cost; nothing in the renderer can lower it.
* large-single-page: one parsed page is 190 MB and the first tile takes 350 ms (peak 220 MB). It is
  released 1.5 s after the last request. Splitting the content stream into tiles is still a v0.4+ item.
* The peak figures are for a hostile scroll (no pause between pages, four tiles per page); real use is
  slower.

## Root causes (what the first run had wrong)

1. **libmalloc never gives freed memory back on this macOS.** A plain C program that frees eight 26 MB
   blocks keeps all 209 MB resident, and `malloc_zone_pressure_relief` returns 0
   (`MallocSpaceEfficient=1` or `MallocLargeCache=0` in the environment at process start: 1 MB). The
   variable is read once before `main`; `setenv` followed by `malloc_create_zone` has no effect, and
   re-ordering the default zone does not either. So the host must start the renderer with
   `papyrine_render::mem::CHILD_ENV` in its environment (`ChildSpec::env`), or call
   `mem::reexec_if_renderer()` as the very first line of `main` (before `bootstrap()` applies the sandbox;
   the sandbox denies `exec`). This is what the first run's "633 MB of empty malloc regions" and
   "pressure relief returns 0" were. It also cuts PDFium's cost of opening large-objects from 137 to 100 MB.
2. **PDFium's page cache holds each page's decoded images**: eight cached pages of a 2480 x 3508 RGB scan
   are 8 x 25 MB = 200 MB. Closing pages promptly is what matters, not the cap of 8 itself. An image-heavy
   document therefore needs a cache of one or two pages; a text document is happy with eight.
3. **The document's object store is released only by closing the document** (about 25 KB per text page,
   about 0.2 MB per image page). Closing and re-opening (recycling) is cheap through `MultiBuf`.
4. **The "238 MB peak while opening" of large-objects in the first run was the final re-open**, which
   opened the new document before closing the old one (two copies). A plain open peaks at 137 MB (100 MB
   after parsing, with the allocator environment). The role now closes first for documents whose parse
   state is large (peak 138 MB instead of 237 MB over 50 re-opens).

## The policy (crates/papyrine-render `governor.rs`, `role.rs`)

Thresholds are growth of the process footprint above what the open documents cost by themselves
(`open_cost`, measured at open), so a document that is expensive to open does not trigger recycling:

* before parsing a page that is not cached: growth over 64 MB, or 256 page parses since the last open,
  re-opens the document first (recycle); over 32 MB closes the other cached pages. A recycle that frees
  less than a quarter of the growth backs off for 64 cold loads (a platform that keeps freed memory
  must not thrash).
* after every job: growth over 32 MB shrinks the page cache to the active page.
* 1.5 s without a job: close every page; recycle if growth is over 8 MB; ask the allocator to return memory.
* 3 s without a job: **hibernate** documents whose open cost is 24 MB or more (drop the PDFium document;
  page count, sizes and the sections are kept; the next request re-opens, 140 to 340 ms for
  large-objects, under 50 ms for anything else).
* `FPDF_RENDER_LIMITEDIMAGECACHE` and `FPDF_RenderPage_Close` were already in place. Tiles are always
  at most 512 x 512 so bitmaps are bounded by construction (banding is moot); previews are refused above
  4096 px. There is no image-decode cap: PDFium decodes inside `FPDF_RenderPage`, so a hostile 100 MP
  image can only be bounded by the child's memory limit (`ChildSpec::memory_limit`) and crash restart.
* Text cache: 3 MB, LRU; search never fills it.

## Proposed ADRs and design changes

1. **ADR (renderer memory policy).** Adopt the governor above: footprint-relative thresholds, page cache of
   one to eight pages by weight, recycle, idle close, hibernate at 24 MB open cost. Amends ADR-009's
   "PDFium page cache 8 pages" to "up to 8 pages, fewer when heavy".
2. **ADR (macOS allocator).** The renderer child is started with `MallocSpaceEfficient=1`
   (`papyrine_render::mem::CHILD_ENV`) and the gate fails without it. Needs one line in each launcher
   (`crates/papyrine-app/src/spawn.rs`, `apps/desktop/src-tauri/src/supervisor.rs`) or
   `papyrine_render::mem::reexec_if_renderer()` first in both `main`s. Also worth checking the engine and
   the host: the same libmalloc behaviour may hold memory there.
3. **Engine must not enumerate objects** and **large-object documents open view-only with the lazy engine**
   (unchanged from the first run; the engine is now the largest cost on large-objects).
4. **Wire change for selective invalidation.** `RenderRequest::Reopen` carries no dirty-page list, so the
   renderer drops its text cache for the whole document on every re-open and cannot say which pages
   changed. Add `dirty_pages: Option<Vec<u32>>` (and a priority byte on `RenderTile`/`RenderPreview`: the
   renderer currently infers it, see `role.rs`). Tile caches live in the host broker, which already
   invalidates by `ChangeSetSummary::dirty_pages`; the renderer itself holds no tile cache.
5. **Build the 1.2 test as a CI job on macOS and Linux** with real shell and broker numbers
   (`memprobe gate` is the renderer/engine half; `run.py --large-json` writes the rows
   `tools/check-budgets --large-doc` reads).

### Method

Probe: `bench/memory` (crate `memprobe`, standalone, own `[workspace]`), driven by
`bench/memory/run.py`, one fresh process per measurement so peaks cannot leak between runs.

- **Metric:** macOS `phys_footprint` of the probe process (what Activity Monitor and the gate use;
  clean file-backed pages of the input mapping are not counted). Peak is the larger of the
  kernel's lifetime peak (`ledger_phys_footprint_peak`) and a 10 Hz sampler. "Settled" is 10 s
  after the last operation, no interaction. An empty probe process is 1.7 MB.
- **Files:** the four generated benchmark files (`tools/gen-corpus`), plus `large-objects-objstm`
  (the same 1.6 M objects in object streams, 25 MB) and `typical-20p`.
- **qpdf (papyrine-cos):** open the file, then resolve every page object, its `/Contents`,
  `/Resources` and `/MediaBox`. Input is either an mmap handed to `Document::open_bytes` (the
  closest to the design; a true `InputSource` over the shared mmap is not in `papyrine-cos`
  yet) or `Document::open_path`. Results for the two are within 1 MB except as noted.
- **PDFium (papyrine-render):** `Document::open` over a read-only mmap
  (`FPDF_LoadCustomDocument`), then `render_preview` of every page in order at 160 px longest
  edge (page cache of 8, cancel never fires). Rendering at preview size keeps raster memory
  small; image decode and page parsing, which dominate below, do not depend on output size.
- **Not done:** zoomed tile rendering at screen scale, whole-document search, edits, the webview
  and host processes, Linux and Windows.

### What the PDFium numbers are

- **Growth is proportional to pages touched, and it is retained until the document is closed.**
  Text: 104 MB over 2,000 pages, about 50 KB per page. Images: 645 MB over 1,000 pages. The
  design says "PDFium caches are capped (page cache of 8 pages)". That cap exists and is
  working, but it is not the cache that matters: PDFium keeps every indirect object it has
  parsed (content streams, fonts, image streams) in the document, and the page cache cap does
  not touch that. For the image file `vmmap` on the finished process shows 443 MB in small
  malloc regions plus 199 MB in large ones (consistent with 8 cached pages of 25 MB decoded
  RGB, about 200 MB, and the compressed image streams, about 444 MB, of the whole file). The
  split between the two is my reading of the vmmap output, not a profiler result.
  This undermines "No heap copy of the file in either process": for an image-heavy document
  PDFium does end up with the file's stream bytes on its heap.
- **Closing the document frees it for text, not (yet) in the footprint for images.** After
  `reopen()` the text file drops from 104 to 15 MB. For images `vmmap` shows the heap
  allocated size falling to 0.6 MB while 633 MB of "empty" malloc regions stay resident and
  `malloc_zone_pressure_relief` returns 0. The footprint therefore does not come back, but it
  also stops growing: freed blocks are reused. The practical effect of re-opening is to cap
  the high-water mark.
- **Re-open interval** (large-1000p-images, peak = settled): never 648 MB, every 200 pages
  335 MB, every 50 pages 250 MB (242 MB in an earlier run), every 20 pages 228 MB, every 5
  pages 141 MB. For text: every 5 pages 14.5 MB, every 50 pages 19.4 MB. A re-open of a normal
  document is 0 to 2 ms (46 ms right after the 2,000-page scan); of the 1.6 M-object file it is
  about 220 ms (cost of re-reading the xref).
- **large-objects costs PDFium 135 MB just to open** (its cross-reference table, about 85 B per
  entry) with a 100 MB transient on top. Nothing in the renderer design can lower that except
  not opening such a file in PDFium.
- **large-single-page: 259 MB is one parsed page** (400 k page objects, about 650 B each). It
  is the page cache entry, which is why closing the page set recovers 177 MB. Tile rendering
  parses the same page, so zooming will not avoid it.

### qpdf: does the object table dominate on large-objects?

Yes, and only there. Opening the 1.6 M-object classic-xref file costs 100 MB (the xref and
object table: about 62 bytes per entry) and 131 MB for the object-stream variant (entries plus
the stream index). Everything else (pages, 1,000 or 2,000 of them) is under 10 MB, so the
object table does not matter for ordinary documents. Resolving every object costs a further
1.0 GB.

### Lazy per-operation QPDF fallback, quantified

Measured with `memprobe cos-lazy`: five "operations" in one process, each opening the file,
resolving one page and dropping the document.

| File | per-operation time | peak | settled after drop | versus eager (settled) |
|---|---:|---:|---:|---:|
| large-objects | 205 to 214 ms | 100 MB | **36 MB** | 100 MB: saves 64 MB |
| large-objects-objstm | 219 to 221 ms | 131 MB | **65 MB** | 131 MB: saves 66 MB |
| large-2000p-text | 6 to 10 ms | 6.8 MB | 6.8 MB | 8.3 MB |
| large-1000p-images | 3 to 4 ms | 5 MB | 4.8 MB | 5.8 MB |
| typical-20p | under 1 ms | 1.9 MB | 1.9 MB | 1.9 MB |

Conclusions: the lazy mode **does not lower the peak** (the same table is built every time),
**halves the settled figure** on the 1.6 M-object files because the allocator hands back part
of the table, and **costs about 0.2 s per operation** there. It does nothing for the real
risk, which is a whole-document operation (full rewrite, Save As, `object_count`): that
resolves all objects, 1.1 GB, eager or lazy. Recommendation: do not build the lazy fallback
now. Use it only for view-only documents above roughly 500 k objects, if at all; the edit path
for such files must use the incremental writer and never enumerate every object.

### Proposed ADRs and design changes (first run; superseded above)

1. **Renderer memory policy (new ADR).** Correct section 1.2: PDFium's cache that matters is the
   per-document parsed-object store, not the page cache. Adopt a policy in the renderer role:
   re-open the PDFium document every N pages loaded (start with N = 5 for image-heavy files, N = 50 otherwise: 141 and about 20 to 250 MB measured) and after every large idle. For the
   image file this still leaves the renderer above 120 MB; the measured floor of about 140 MB
   is transient image decode at preview size. The owner has to choose between raising the
   renderer budget for image-heavy files (about 150 MB), or restarting the renderer *process*
   when its footprint passes a threshold (the only way to give memory back to the OS, since the
   allocator keeps empty regions), accepting a re-render of the visible tiles (tens of ms).
2. **Engine must not enumerate objects.** `Document::object_count`/`object_ids` and any
   whole-document walk are forbidden on the open and view paths (qpdf resolves all objects:
   about 1.1 GB for 1.6 M objects). Add a gate: no call on the open path (a test over the host
   call graph, or a counter in `papyrine-cos` under test).
3. **Large-object documents.** Above about 500 k objects show a banner and open in view-only
   mode with the lazy fallback; disable "optimize" and full-rewrite save, offer incremental
   save only. PDFium's own 135 MB for such files exceeds the renderer budget regardless; state
   a budget exception for them in section 1.1 rather than pretend otherwise.
4. **Single-page vector monsters** (261 MB for 400 k elements): budget exception, or tile-level
   content-stream splitting (a v0.4+ item). Not worth solving before v0.1.
5. **Build the section 1.2 test script** as a CI job on macOS and Linux (needs PSS accounting in
   the probe; the process attribution code from Spike 0.1 `measure-shell.mjs` can be reused).
