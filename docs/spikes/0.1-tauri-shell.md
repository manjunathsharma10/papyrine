# Spike 0.1: bare Tauri 2 shell (macOS, Windows, Linux)

Status: done. Measured on the reference Mac and in GitHub Actions
(run 37003221829, commit ad641f9; earlier runs 36998796613 and 37002224171
agree with it).

## Verdict against ARCHITECTURE section 1.1

| Budget | macOS arm64 (reference Mac) | Windows x64 (CI) | Linux x64 (CI, Xvfb) |
|---|---|---|---|
| Installer <= 50 MB (AppImage <= 100 MB) | dmg **2.0 MB**: pass | msi 2.6 MB, NSIS 1.7 MB: pass | deb 2.0 MB, rpm 2.0 MB, AppImage **77.0 MB**: pass |
| Cold launch < 1.0 s, warm < 0.5 s | median **0.35 s**, p95 0.38 s: pass | median 0.62 s (runner): pass | median 0.39 s (runner): pass |
| Idle memory <= 150 / 175 / 200 MB | **77 MB**: pass | 68 MB: pass | **260 MB: FAIL** (see below) |
| Initial JS <= 200 KB gzip | 45.4 KB: pass | same | same |

**One budget is broken by the bare shell alone: Linux idle memory.** On the CI
runner the shell uses 260 MB of PSS (budget 175 MB). Setting
`WEBKIT_DISABLE_DMABUF_RENDERER=1` brings it to 185 MB, still over. Caveats,
because the number is not yet trustworthy as a verdict:

- The runner is headless: Xvfb with Mesa llvmpipe (software GL), no GPU. A
  real desktop will differ.
- PSS charges each process the file-backed pages of the shared libraries
  (WebKitGTK, GTK, Mesa) in full when nothing else on the machine maps them.
  Split of the 260 MB: about 144 MB file-backed, about 111 MB anonymous (host
  24.6, networking 7.5, web process 78.7). With DMABUF off it is about 125 MB
  file-backed and about 59 MB anonymous.
- The shared-library part is a property of how the budget is accounted (PSS on
  a machine with no other WebKit/GTK apps), not of Papyrine code.

The lead should report this to the owner. Options: verify on a real Linux
desktop with a GPU (needs the owner's hardware), accept an adjusted Linux
budget, or account anonymous memory only for Linux. Nothing was changed in
the budget table here.

## What was built

- `apps/desktop`: Tauri 2 + React 18 + strict TypeScript + Vite 7. Runtime
  deps are `react`, `react-dom` and `@tauri-apps/api` only.
- `apps/desktop/src-tauri` (crate `papyrine-desktop`, binary `papyrine`, bundle
  id `io.github.manjunathsharma10.papyrine`, product name Papyrine), added to
  the workspace. Tauri features: `wry`, `compression`, `common-controls-v6`;
  no plugins, no devtools, no tray.
- Tile transport (ADR-009 shape): Rust serves `papyrine://localhost/tile/{page}/{x}/{y}`
  as raw 512x512 RGBA (1 MiB); the UI fetches it, builds an `ImageData`,
  `createImageBitmap`, draws on a canvas. On Windows WebView2 maps custom
  schemes to `http://papyrine.localhost`; the client handles that.
- Launch tracing: the UI calls `first_tile_painted("drawn")` right after
  `drawImage` and `("presented")` two animation frames later. The host prints
  both with epoch milliseconds when `PAPYRINE_TRACE` is set. A `ui_error`
  command surfaces UI failures in the same trace.
- `apps/desktop/scripts/measure-shell.mjs`: cross-platform measurement (see below).
- `.github/workflows/spike-shell.yml`: matrix build and measurement.

## Method

- **Launch**: wall clock from just before the launch call to the host receiving
  `presented`. On macOS the `.app` is started through LaunchServices (`open -n`,
  like Finder). Elsewhere the binary is spawned directly. Internal spawn to
  `main()` is 5 to 45 ms depending on the path.
- **Idle memory**: sum over every process of the app, 10 s after first paint:
  macOS `phys_footprint` (`footprint --json`), Linux PSS (`smaps_rollup`),
  Windows private working set (WMI perf counters). macOS WebKit helpers
  (WebContent, Networking, GPU) are XPC services with parent pid 1; they are
  attributed with the private `responsibility_get_pid_responsible_for_pid`
  call (what Activity Monitor uses), with a "new since launch" fallback when
  that gives none (used on the CI runner only).
- **JS size**: gzip of `dist/assets/*.js`.
- **"Cold" launch**: `sudo purge` needs a password and was not available. The
  approximation is the first launch after the build plus the first run in each
  series; neither empties the page cache, so it is a lower bound on true cold.
  Gatekeeper first-run verification is excluded because the local build is
  unsigned and not quarantined.

## macOS arm64 (this Mac: M4, 16 GB, macOS 27)

Measured on the release bundle built by `pnpm tauri build --bundles app,dmg`.
Load average during the final series was 4.3 to 4.5 (other engineers were
compiling; a lower-load repeat was not possible during the session).

| Item | Value |
|---|---|
| `Papyrine.app` | 5.06 MB (binary 5.05 MB) |
| `.dmg` (aarch64) | 2.01 MB |
| JS bundle | 140.2 KB raw, **45.4 KB gzip** (+ 0.2 KB CSS) |
| Launch to first tile, 20 runs | first 334 ms, **median 351.5 ms**, p95 383 ms, min 324 ms, max 406 ms |
| Idle memory, 5 runs | **77.4 MB median** (77.4, 80.9, 77.4, 70.5, 80.1) |
| Idle breakdown (last run) | host 32.2, WebContent 26.5, GPU 15.7, Networking 5.8 MB |

Observations: under heavy load (load average 8 to 13) single launches took
0.76 s and, right after a rebuild, 1.8 s. One run in 20 never produced an
animation frame (window occluded) and used the `drawn` stamp; a handful of
launches in other series produced no paint at all because another session had
a background `pkill -x papyrine` loop running on this Mac (see Follow-ups);
those series were discarded and the final series ran from a copy of the
bundle with a renamed executable.

## Windows x64 (GitHub `windows-latest`, WebView2)

msi 2.55 MB, NSIS setup 1.72 MB, binary 7.18 MB. Launch median 624 ms
(first 3.2 s, includes WebView2 start-up on a cold runner). Idle 67.8 MB
private working set over 7 processes (6 `msedgewebview2` plus the host).
Runner hardware is not the reference machine; the budget on Windows is a
trend gate.

## Linux x64 (GitHub `ubuntu-22.04`, WebKitGTK 4.1, Xvfb + dbus session)

AppImage 76.96 MB (budget 100 MB, so 23 MB headroom), deb 2.05 MB, rpm 2.05 MB,
binary 5.32 MB. Launch median 389 ms (first 678 ms). Idle by variant, same
runner:

| Variant | Idle PSS | Web process |
|---|---|---|
| default | 259.8 MB | 165 MB |
| `WEBKIT_DISABLE_DMABUF_RENDERER=1` | 185.4 MB | 93 MB |
| plus `WEBKIT_DISABLE_COMPOSITING_MODE=1` | 186.7 MB | 93 MB |
| plus `LIBGL_ALWAYS_SOFTWARE=1` | 185.6 MB | 93 MB |

Without a D-Bus session bus (plain `xvfb-run`) every launch took 25 s (an
accessibility/portal call times out); with `dbus-run-session` it is 0.4 s.
Real desktops have a session bus; the workflow now provides one. `NO_AT_BRIDGE=1`
alone did not help.

Flatpak was not built: it needs a flatpak-builder manifest against an
org.gnome.Platform runtime with offline cargo and pnpm sources, which is
packaging work for v0.1 (the AppImage/deb/rpm numbers already show the
payload is tiny; the runtime is not counted in a Flatpak bundle's size, so
the Flatpak size budget is not at risk). Not measured, so not claimed.

## Local build notes

- `pnpm tauri build --bundles app,dmg` needs `CI=true` when no Finder is
  available (it skips the AppleScript window styling step). A stale
  `bundle/macos/*.dmg` or `rw.*.dmg` makes `hdiutil convert` fail with
  "File exists"; delete them. `bundle.licenseFile` must not be set: it adds an
  EULA step that fails in `create-dmg` here.
- Release build of the shell (cold cargo cache, 4 jobs): about 90 s.
- Not measured here: arm64 Windows, x64 macOS, Linux arm64 (CI matrix of
  v0.1.1 covers them).

## Proposed ADRs

1. **Launch measurement path**: macOS launch is measured via LaunchServices
   (`open -n`), helpers attributed by responsible pid; `first_tile_painted`
   has `drawn` and `presented` stages and the gate uses `presented`.
2. **Linux idle-memory accounting and renderer flags**: decide between
   (a) verifying on a real GPU desktop, (b) setting
   `WEBKIT_DISABLE_DMABUF_RENDERER=1` at startup on Linux (saves about 75 MB
   on the CI runner; widely used workaround, but changes GPU compositing for
   all Linux users), (c) a Linux budget based on anonymous PSS or a higher
   absolute number. The bare shell is 185 to 260 MB PSS on the CI runner
   against 175 MB.
3. **Windows tile URL**: custom scheme is reached at
   `http://papyrine.localhost/...` (WebView2 behaviour); CSP `connect-src`
   lists both forms.
4. **Frontend toolchain pins**: React 18.3, Vite 7, TypeScript 5.9, pnpm 10
   (via `packageManager`); Tauri 2.12 with only `wry`, `compression`,
   `common-controls-v6`.
