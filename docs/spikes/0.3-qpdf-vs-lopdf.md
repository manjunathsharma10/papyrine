# Spike 0.3: qpdf (papyrine-cos) vs lopdf on the corpus

Status: done. Measured on the reference Mac (Apple M4, 10 cores, 16 GB, macOS 27) on 2026-10-02,
Rust 1.98.1 `--release`, qpdf 12.4.2 (native crypto) through `papyrine-cos` at commit `2ea7ba9`,
lopdf 0.45.0 (latest on crates.io, default features), PDFium 156.0.8076.0 as a page-count oracle.
Nine other engineers were compiling during the runs, so timings are noisy; RSS is not.

## Verdict

**ADR-002 is confirmed: qpdf stays the only object model and lopdf stays rejected.** On the 3,367
corpus files that exist locally (3,286 downloaded plus 81 generated; 100 USCIS form URLs in
`js-forms.toml` answer HTTP 403 from here) qpdf opens more files, repairs more of the damaged
ones, agrees with PDFium on page counts more often, never loads stream data eagerly, and
reports typed errors where lopdf silently returns an empty document. Neither library panicked,
crashed or hung on any file. The one place qpdf is not clearly ahead is memory on a document
with 1.6 million objects, where both are heavy (qpdf 1.0 to 1.3 GB if every object is resolved,
lopdf 1.4 to 1.9 GB always); see "Memory" and `0.2-memory.md`.

## What was compared

For every file a fresh child process opened it, read the page count, resolved every page
object and printed one line. One process per (library, file) so crashes, hangs and peak RSS are
attributable. RSS is `ru_maxrss` from `wait4` (whole process, including the Rust runtime,
about 5.6 MB for an empty process).

| Piece | Path |
|---|---|
| lopdf probe (throwaway, own `[workspace]`) | `spikes/lopdf/src/main.rs` |
| qpdf and PDFium probe | `bench/memory/src/main.rs` (`cos-open`, `pdfium-open`) |
| Runner over the corpus (30 s timeout, 4 jobs) | `spikes/lopdf/compare.py` |
| Large files, serial, 3 repetitions, medians | `spikes/lopdf/large.py` |
| Tables in this document | `spikes/lopdf/summarize.py` |

Reproduce:

```
export CARGO_TARGET_DIR=$PWD/target/memprobe
(cd bench/memory && cargo build --release)
CARGO_TARGET_DIR=$PWD/target/lopdf-spike cargo build --release --manifest-path spikes/lopdf/Cargo.toml
python3 spikes/lopdf/compare.py --lopdf target/lopdf-spike/release/lopdf-probe \
  --memprobe target/memprobe/release/memprobe --out target/spike03-all.tsv
python3 spikes/lopdf/summarize.py target/spike03-all.tsv
```

Definitions. **open**: the library returned a document with at least one page.
**open, 0 pages**: it returned a document but the page tree is empty or unreadable.
**typed error**: it returned an error value (qpdf: `Damaged`, `Pages`, `InvalidPassword`,
`Unsupported`, `Object`, `Native`; lopdf: its error enum). Passwords were not supplied to
either library, so password-protected files are expected to fail with a password error.

Notes:

- **Repair quality**, judged by page count against PDFium on the 766 files tagged
  `malformed` or `mal-*` that PDFium opens: qpdf returns the same count on **722**, lopdf on
  670. qpdf returns a different count on 3 and lopdf on 12. qpdf yields an empty page tree on
  8, lopdf on 54; qpdf errors on 33, lopdf on 30. The only disagreement where both open and
  PDFium sides with qpdf is a set of 6 files (`mal-endobj-missing`, `bad_page_type`, two
  oss-fuzz files, `issue7229`, `mal-xref-single-entry-wrong`): qpdf finds 2 or 3 pages where
  lopdf stops at 1 or 2.
- **lopdf's "open, 0 pages" is a silent failure.** Of its 182, 69 are encrypted files (66 of
  them password-protected: `Document::load` succeeds and the caller must remember to decrypt;
  qpdf returns `InvalidPassword`). The other 113 are damaged files that load as empty
  documents. A product built on that needs its own validity layer on top of the parser; with
  qpdf the typed error is the validity layer.
- **lopdf has xref reconstruction** (0.45 added it) but it fails where the trailer is gone:
  all five truncation cases (`mal-truncated-half`, `-mid-stream`, `-no-eof`,
  `mal-xref-missing`, `mal-trailer-missing`) fail in lopdf with a parse error and are repaired
  by qpdf with 4 to 9 logged repairs.
- **Where lopdf wins** (opened by lopdf, not by qpdf): 11 files. Five are real recoveries qpdf
  does not make: `mal-objstm-n-too-large`, `pdfjs/bug1011159`, `pdfjs/issue16091`,
  `pdfjs/issue4573`, `qpdf/minimal-linearize-pass1` (qpdf raises `Damaged` when an object
  stream or linearization hint is bad, even though the page objects are intact). The other six
  are page-tree oddities (`Pages-tree-refs`, `pages-loop`, `no_page_count`,
  `bug1811668_reduced`, `Brotli-Prototype-FileA`, one oss-fuzz file) where qpdf reports a
  `Pages` error or zero pages and lopdf finds a page. Opposite direction: qpdf opens **85** files
  lopdf does not.
- qpdf's 177 typed errors: 77 `InvalidPassword`, 70 `Damaged`, 24 `Pages`, 4 `Unsupported`
  (the non-Standard security handler in four PDFBox files), 1 `Object`, 1 `Native` (a page tree
  node loop surfaced as a generic native error: see follow-ups).
- A per-file TSV for both libraries and PDFium is produced by `compare.py`
  (`target/spike03-all.tsv`, 10,101 rows; not committed).

## Peak RSS and time

Across all files that open, medians are the process floor (qpdf 6.1 MB, lopdf 6.4 MB;
p95 9.1 and 12.4 MB). Wall time is dominated by process start: median about 10 ms for both
(the runner polls at 5 ms). The differences are in the large files.

Reading it:

- **lopdf reads the whole file into the heap**: 873 MB of RSS for the 444 MB image file,
  because every stream is loaded at `load` time. qpdf stays at 9 MB (it reads stream bytes on
  demand). This is the property ARCHITECTURE section 1.2 depends on; lopdf cannot meet it
  without a stream filter (`load_filtered`) that discards data and re-reads it later, which
  is custom work on its internals.
- **Both are slow to open 1.6 M objects** (qpdf 0.3 s and 104 MB for the xref table alone;
  lopdf 0.6 to 0.7 s and 1.8 GB), and qpdf's `getAllObjects` (behind `Document::object_count`)
  resolves every object: 1.0 to 1.3 GB and 2 to 3.5 s. The engine must not call it on open;
  details and the lazy fallback in `0.2-memory.md`.
- **Time to first object** (page count) is 6 to 12 ms for the 1,000 to 2,000 page files in
  qpdf (it walks the page tree and loads each page dictionary), under the timer resolution in
  lopdf because the work already happened in `load`. End to end qpdf is faster or equal on
  everything except the two 1.6 M-object files, where lopdf's parallel (rayon) parse beats
  qpdf's single-threaded `getAllObjects` but at 1.4 to 1.8 GB.

## Findings in papyrine-cos (qpdf behaviour), not blockers

1. **Bug, test written (ignored):** rewriting a document whose trailer qpdf had to recover from
   nothing produces a file whose trailer lacks `/Size`, so it needs repair again on the next
   open. Affects `mal-trailer-missing`, `mal-xref-missing`, `mal-truncated-half`,
   `mal-truncated-mid-stream`, `mal-truncated-no-eof` (28 files across the third-party corpus
   show `rewrite not clean: 3` in the acceptance run). The qpdf CLI behaves the same. Fix: in
   `Document::write`, when the trailer has no `/Size`, set it to the highest object number + 1
   before writing (verified in a scratch copy: the rewrite then reopens with an empty repair
   log). Test: `corpus_rewrite_of_trailerless_file_is_clean` in
   `crates/papyrine-cos/tests/corpus_acceptance.rs`, `#[ignore]` so CI stays green until the
   fix lands.
2. **Silent page loss:** `mal-pagetree-kid-missing-object.pdf` opens with 2 of 3 pages and an
   empty repair log (PDFium sees 3). A missing kid object should produce a repair entry.
3. `PDFBOX-6040-nodeloop.pdf` fails as `Error::Native("/Count is wrong after flattening pages
   tree")`; it is a page-tree problem and should map to `Error::Pages`.
4. Recovery gaps relative to lopdf: bad object-stream metadata (`/N` too large, `/First` wrong)
   and bad linearization hints end in `Damaged` although the page objects can be read (list
   above). Worth a qpdf-side retry without object streams only if real users hit it.

## Recommendation

Confirm ADR-002. Add to its Consequences: (a) the engine must not call
`Document::object_count`/`object_ids` on open or in view-only paths (qpdf resolves every object);
(b) the three papyrine-cos follow-ups above. lopdf is not needed as a fallback parser: the
files it opens and qpdf does not are 11 of 3,367 (5 of them real recoveries), and adopting it would reintroduce a second
object model (the thing ADR-002 exists to avoid).

Not measured here: lopdf's writer, incremental update and encryption writing (the spike was
about open, repair, memory and time-to-first-object, per ROADMAP 0.3), and password handling
(no passwords were supplied to either library).
