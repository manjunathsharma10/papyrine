# Spike 0.2 (renderer half): B1-renderer

Status: measured on macOS only. Windows and Linux are not measured; `tools/fetch-pdfium`
already pins their PDFium builds, so the same harness runs there once CI has a matrix job.

## What was measured

ARCHITECTURE section 4.6 asks whether "snapshot sections appended to a base file, re-opened
in PDFium" meets the edit budget, before we commit to command mirroring. This harness
(`crates/papyrine-render/examples/b1.rs`) measures the renderer half:

- time to open `base ‖ section₁ … sectionₖ` through `FPDF_LoadCustomDocument` (no heap copy
  of any buffer; base and sections are read-only mmaps), k = 1..64, section size 1 KB..64 MB;
- time to the first tile after open (page 0 and a cold page in the middle of the document);
- a 500-edit session (one section per edit, L1 merge when k > 16, the edited page's tile
  rendered after every edit): edit-to-tile latency and memory growth;
- memory as macOS `phys_footprint` (`task_info(TASK_VM_INFO)`), the number the section 1.1
  budget gate uses. File-backed clean mmap pages are not counted, which is the point of the
  design. A self-check at the top of each run confirms the metric moves 64.0 MB when 64 MB
  of heap is touched.

Reproduce: `tools/fetch-pdfium && cargo run --release -p papyrine-render --example b1`
(`--quick` caps the matrix at 64 MB total, `--session` runs only the edit sessions).
Generated PDFs live in `third_party/cache/render-bench/` (gitignored).

## Environment

- Apple M4, 10 cores, 16 GB, macOS 27, Rust 1.98.1 `--release`.
- PDFium 156.0.8076.0 (bblanchon/pdfium-binaries `chromium/8076`, no V8, no XFA),
  loaded dynamically through `pdfium-render` 0.9.4 (`pdfium_7881` binding set; all symbols
  resolved against the 8076 build).
- `libpdfium.dylib`: 7,278,480 bytes (6.94 MB); the downloaded archive is 3.49 MB. Loading
  it costs about 0.5 MB of footprint.

## Documents

Both are generated in code (`papyrine_render::testgen`), uncompressed classic-xref PDFs, deterministic.

| name | pages | size | per-page content |
|---|---|---|---|
| typical-20p | 20 | 0.3 MB | 50 lines of 10 pt Helvetica, 300 filled rectangles |
| large-2000p-text | 2000 | 50.8 MB | 50 lines of 10 pt Helvetica, 600 filled rectangles |

The 1,000-page image-heavy file from section 4.6 is not covered here (needs the corpus
generator's image path); it is a follow-up.

Each section replaces page 0's content stream and carries an unreferenced filler stream of
the stated size. The filler makes the section file as large as requested, but PDFium never
reads it, so the matrix mostly shows that re-open cost depends on the xref chain, not on
section bytes. Real sections contain objects the renderer does read when the edited page
is drawn; that cost is in the "tile" columns only for the small replaced content stream.

## Results

### Headline

| target (section 4.6) | measured here | verdict |
|---|---|---|
| edit → visible tile < 100 ms p95 | renderer only: 0.8 ms p95 (20 pages), 7.7 to 11.9 ms p95 (2000 pages) | pass with a wide margin; excludes qpdf commit, IPC, `papyrine://` transport, GPU upload |
| renderer RSS growth < 10 MB over 500 edits | 0.0 to 0.1 MB (20 pages), 0.6 to 1.0 MB (2000 pages), measured after edit 50 | pass |
| re-open, k = 1..64, any section size | 0.01 to 0.17 ms (20 pages), 0.4 to 0.6 ms (2000 pages); flat in section size | pass; L1 merge threshold of 30 ms is never approached |

On this evidence command mirroring (the section 4.6 fallback) is not needed for the
renderer. Caveats: the test documents are synthetic text and vector pages, the edited
page is cheap to draw, and only one platform was measured. Re-run B1 on Windows and Linux
and with the image-heavy file before closing the question.

## Observations

- **Re-open is O(xref chain), not O(file).** PDFium parses the cross-reference chain
  and reads objects lazily, so a 64 MB section that holds a 1 MB-page edit and an unread
  filler costs the same as a 1 KB section. Each additional section adds about 2.5 µs
  (20 pages) and 2.4 µs (2000 pages). 64 sections cost 0.17 ms to 0.6 ms.
- **The 2000-page document costs about 0.4 ms more than 20 pages to open** (page-tree and
  xref size), and 4 to 5 ms for the first tile of a never-touched page (page-tree walk plus
  parsing a 25 KB content stream).
- **Memory is flat.** Mapped sections are not counted until touched; open + tile of
  a 64 MB x 8 section set (512 MB mapped) adds 0.1 MB. A 500-edit session grows the
  footprint by at most 1 MB.
- **Cold start is the visible cost.** The first tile of the process takes 21 to 26 ms
  (up to 123 ms on the very first run after a build, with a cold file cache): PDFium
  initialises its font mapper on first text draw. Later tiles are under 1 ms for simple
  pages. Warm this up in the background at app start (render a 1x1 text tile) so it
  never lands on the first page view.
- `page_sizes()` for all 2000 pages takes 8 to 70 ms depending on cache state; prefer
  lazy per-page sizes (`page_size(i)`) or a size table from the engine.
- Cancellation works through `FPDF_RenderPageBitmap_Start` + pause callback:
  a cancel at the first poll returns after about 1.1 to 1.4 ms (the time to
  reach the first pause point). PDFium polls between page objects only, so one huge
  image or shading is not interruptible.
